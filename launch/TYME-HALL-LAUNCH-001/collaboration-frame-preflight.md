## Authority grammar — one direction only

PUBLIC READER → optional UNTRUSTED REPORT → EVIDENCE TRIAGE → REVIEW CANDIDATE → authorised human review → proposed Work/Branch transition → optional repository PR → independent technical assessment → separate human release decision → deployment observation and trace.

No edge in this sequence may be inferred merely from the previous state.

1. A public GitHub issue is a repository-native artifact; it is NOT a Hall Event Envelope or proof of Office admission. Raw contributor prose, URLs, screenshots and agent text are untrusted input.
2. An Office Contribution Trail entry is a provenance/review projection, not automatic Canon or institutionally approved Work. Inherited Office routing and Work Registry remain primary; no duplicate contribution registry.
3. A GitHub PR is a proposed source change. Green CI, a bot review or an eligible human GitHub approval do NOT authorize production deployment, public publication, model privileges, money, or canonization.
4. A reviewed finding may improve epistemic standing, but authority requires its own explicit actor, scope, evidence, time and approval source.
5. Participant autonomy includes safe exit and a clear choice about continuity; NEVER silently turn temporary session state into persistent identity or data capture.

| Role | Entry | May do | Must NOT do |
|---|---|---|---|

| Public technical evaluator | Public data only | Cold-read/issue findings; record raw evidence | No GitHub required-approval credit or privileged access |
| Qualified code reviewer | Human-screened; repo-scoped eligible permission separately approved | Approve/request changes with reproducible findings | No admin/Cloudflare/Notion access, ruleset bypass, final release GO |

Reviewer permission may require repository write access to count under GitHub's rules. That is consequential access to development branches; inspect eligibility and revocation before inviting. Never add a broad bypass actor for convenience.

## Minimum founder decisions (do not infer answers)

**D1 — Rights and license:** select code license, scroll/text/media license, brand/trademark terms, contributor attribution and DCO/CLA/permission policy. Distinguish educational read access from permission to redistribute or make derivative works. Obtain appropriate legal advice if rights are contested.

**D2 — Private disclosure:** choose and verify a private vulnerability intake (e.g., GitHub private reporting if actually enabled), responsible human contact, initial response/containment expectation and escalation. Never publish sensitive reports into normal GitHub Issues.

**D3 — Privacy and continuity:** approve GitHub/public disclosure warning, minimal return data, consent, default retention, redaction and deletion limitations, local/session behavior and eventual participant-controlled continuity model. No universal identity registry.

**D4 — Human access and succession:** define eligible reviewer criteria, repo-scoped invitation, approval checks, removal, independent successor/human emergency authorization and role custody. No standing admin bypass.

**D5 — Public intake moderation:** approve issue-template language, behavior rules, security routing, locking policy, duplicate triage and participant appeal/response limits. Templates are presentation controls, not a technical defense against API spam.

**D6 — Release recovery:** assign rollback operator, rehearse staging revert, independently confirm Cloudflare/commit fingerprints and source-health, and define degraded static safe mode.

No financial bounty should be advertised or funded until D1–D5 are answered and a separate amount, contract, payout and adjudicator are authorized.
