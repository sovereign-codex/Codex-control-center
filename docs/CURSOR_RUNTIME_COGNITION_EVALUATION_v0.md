# CURSOR_RUNTIME_COGNITION_EVALUATION_v0

Status: post-bootstrap evaluation contract  
Dependency: Hall Core 0 accepts GitHub observation events  
Authority: none; this does not authorize connecting repositories to Cursor

## Governing question

Does Cursor add durable runtime cognition worth retaining as a federated TYME Hall
platform, or is its strongest value as training wheels and a reference experience from
which TYME, the Notion Office, GitHub Actions, Hall publishing, and institutional dynamics
should learn?

The likely answer is layered rather than binary.

Cursor resembles:

```text
Branch Laboratory
+ Fabricator cohort
+ code-aware AVOT runtime
+ partial review participant
+ mobile steering surface
```

It does not automatically become TYME cognition, Hall Core, Office interpretation, Value
Kernel, accepted memory, institutional authority, Archivist/TRACE, or succession memory.

## Evaluation passes

### Pass 1 — bounded fabrication

Give Cursor one already-commissioned repository task. Require:

- branch and exact commit SHA;
- pull request;
- tests and results;
- artifacts or logs;
- unresolved findings;
- no direct write to `main`;
- no Droplet root credential or Hall ledger secret;
- no deployment or promotion authority.

Hall Core observes resulting GitHub events independently of Cursor's transcript.

### Pass 2 — reconstruction without hidden conversation

A different steward must reconstruct:

```text
what was commissioned
-> why Cursor was bound
-> what authority it held
-> what changed
-> what evidence returned
-> what remains valid next
```

Cursor conversation may be supporting evidence, but reconstruction must not depend on
proprietary memory.

### Pass 3 — extract capabilities, not ornament

| Cursor experience | Candidate institutional destination |
|---|---|
| Cloud agents | federated AVOT/participant adapter |
| Mobile steering | CIT commission and follow-up surface |
| Environment snapshots | reproducible Branch Laboratory contract |
| Parallel agents | bounded multi-participant Work decomposition |
| Rules and hooks | repository-local invariants and conformance |
| Logs, screenshots, videos | Evidence Return Contract |
| Bugbot / agent review | independent review participant |
| OIDC agent identity | short-lived participant binding |
| Automations | Office triggers and GitHub Action conduction |
| Remote desktop | rehearsal and human inspection surface |
| Multi-repository work | cross-repository Work and lineage envelope |

A capability graduates only after repeated use proves it portable and institutionally
meaningful.

## Score each pilot from 0–3

- contract adherence;
- evidence completeness;
- hidden-state dependence;
- authority separation;
- mobile operability;
- cross-repository coherence;
- executor replaceability;
- evidence-based orientation across candidate work surfaces.

## Classification

**Federated Hall platform:** Cursor repeatedly accepts typed Work, exposes stable identity,
works in a reproducible environment, returns attributable evidence, preserves lineage,
respects authority ceilings, and remains replaceable behind the adapter contract.

**Training wheels/reference experience:** its primary value is interface convenience;
reconstruction depends on private transcript; Work and evidence require manual translation;
or authority boundaries survive only as prompt language.

**Specialist executor:** Cursor remains an excellent code Fabricator without becoming the
institution's cognition or runtime center. This is a valid and likely outcome.

## Experience-to-institution rule

```text
use Cursor
-> observe what materially reduces friction
-> require evidence
-> name the underlying capability
-> encode a portable contract
-> reproduce it through TYME / Office / GitHub / Hall when justified
-> keep or replace Cursor according to evidence
```

The first Cursor pilot may begin only after Hall Core has accepted and replayed one GitHub
event correctly, produced one verified backup, exposed the exact deployed commit, and
demonstrated credential separation.
